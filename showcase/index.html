01 — THE IDEA

The point was never to out-Redis Redis.

The point was to turn invisible infrastructure into decisions you can inspect, benchmark, break, and improve.

Radish began as a learning exercise and grew into a compact database system. Instead of wrapping an existing engine, it implements the full path from a TCP byte to a durable mutation.

That scope creates the interesting questions: How do you keep the hot path type-stable? How do multi-key operations avoid deadlock? How can snapshots avoid stopping every writer? What does pipelining reveal about the real bottleneck?

A

Build the mechanism

RESP parsing, linked lists, dispatch, locking, persistence, and the client are implemented in the project—not abstracted away.

B

Measure the boundary

Benchmarks separate raw data structures, full command dispatch, and TCP transport so optimization starts at the actual bottleneck.

C

Name the trade-off

The documentation is explicit about limitations: single-node scope, no rollback, network overhead, and scaling behavior under contention.

02 — ARCHITECTURE

Follow one command.

Every request travels through an explicit, inspectable path. Select a stage to see the decision it owns.

RESP READER / 01 *3\r\n$5\r\nS_SET…

Parse the wire without losing the stream.

A buffered stateful reader decodes RESP frames from TCP, preserves incomplete data across reads, and detects queued commands for the batch path.

  • Incremental socket reads
  • Protocol errors become structured responses
  • Buffered input unlocks pipelining

DESIGN DECISIONS

Small abstractions, sharp responsibilities.

The architecture uses a few reusable mechanisms instead of putting every concern into each command implementation.

store.jl•••
mutable struct RadishStore
  strings::Dict{String, RadishElement{String}}
  lists::Dict{String, RadishElement{DLinkedList}}
  sets::Dict{String, RadishElement{Set{String}}}
  keytype::Dict{String, Symbol}
end
Concrete types on the hot path

Each data type has its own dictionary while one global index enforces one-key-one-type semantics. Julia can specialize operations without boxing values behind Any.

Deadlock avoidance Multi-key commands acquire unique shard IDs in sorted order and release them in reverse.

Writer fairness Once a writer waits, new readers park—preventing a hot read stream from starving mutations.

04 — DURABILITY

Save what changed.
Replay what was not saved.

01

Record

Every successful mutation is appended while its shard lock is held, preserving execution order in the AOF.

02

Swap

The dirty tracker swaps its modified/deleted maps in O(1), letting writers continue on fresh maps.

03

Snapshot

Only affected shard files are rewritten under read locks, then the covered AOF is truncated.

04

Recover

Startup loads sharded snapshots first, then replays the remaining append-only log.

06 — ENGINEERING JUDGMENT

A good project knows its edges.

These are useful interview conversations, not footnotes to hide.

01

Single node by design

There is no replication, partitioning, or cluster consensus. Radish goes deep on one process instead of pretending to be distributed.

Scope choice
02

Atomic execution, not rollback

Transactions lock every involved shard before executing. If a queued command fails, later commands still run; there is no undo log.

Known semantic gap
03

Transport is now the ceiling

In-process execution scales well, but task-per-client networking degrades with many clients. Profiling points toward an evented or sharded I/O layer.

Next architecture
04

Didactical, not production-safe

The system is designed for learning and experimentation. It favors legibility and explicit mechanisms over production completeness.

Intentional positioning

07 — INTERVIEW KIT

Tell the story,
not the feature list.

Start with motivation, zoom into one difficult decision, show what measurement changed, and finish with the limit you would tackle next.

YOUR 90-SECOND VERSION~170 words
“Radish is a Redis-inspired in-memory database I built in Julia to understand the systems work hidden behind a simple GET or SET. I implemented the protocol, storage types, command routing, concurrency, transactions, expiration, and persistence from scratch. The core design uses a typed dictionary per data type, with generic hypercommands handling shared policy like TTL and key semantics before delegating to small type-specific operations. For concurrency, keys hash across 256 read/write lock shards; multi-key operations acquire shards in a stable order, and a custom write-preferring lock prevents starvation. Persistence combines an append-only log with dirty-shard snapshots, so background sync work scales with what changed rather than the whole database. The most valuable result was discovering that the data engine was not the limiting factor: layered benchmarks reached millions of operations per second in process, while TCP throughput was dominated by parsing, scheduling, and writes. That led me to add pipelined batch execution. It is intentionally a learning database, not a production Redis replacement—and the next problem I would explore is the multi-client I/O architecture.”
Why Julia?

It made the type-specialized store and multiple-dispatch command design natural, while its task model gave you real concurrency questions to solve. It was also unfamiliar—which made the project a genuine learning exercise.

What was the hardest invariant?

Keeping store state, the global key-type index, dirty tracking, and AOF order consistent under concurrent commands. The clean answer is to place logging and mutation inside the same ordered shard-lock scope.

How do you prevent deadlocks?

Map all keys to shard IDs, remove duplicates, acquire them in ascending order, then release in reverse. Transactions use the same idea across their full queued command set.

What did benchmarking change?

It showed that optimizing nanoseconds inside the engine would not fix a throughput ceiling in the network path. That evidence justified pipelining and combined batch locking instead.

What would you build next?

Profile and redesign multi-client I/O—likely evented socket ownership or sharded connection loops—before adding more commands. The existing measurements say transport is the highest-leverage boundary.

How would you productionize it?

Add stronger crash-consistency guarantees, binary-safe AOF encoding, fuzz and fault-injection testing, observability, resource limits, replication, and an explicit compatibility contract.
